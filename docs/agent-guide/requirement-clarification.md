# 模糊需求处理流程

> 用户提出的需求经常是模糊的（"这个不好看"、"这里加个功能"）。本文档定义 agent 的澄清和分类流程。

## 一、识别模糊需求

以下特征表明需求需要澄清：

- **指代不明**："这个"、"那里"、"上面"、"刚才那个"
- **主观描述**："不好看"、"太慢"、"有点怪"、"不顺手"
- **缺少边界**："加个功能"（什么功能？加在哪？）
- **缺少验收标准**："优化一下"（优化到什么程度？）

## 二、澄清四步法

收到模糊需求后，**不要直接开始实现**，按以下步骤处理：

### 第 1 步：定位

确定用户说的是哪个具体对象。

**做法**：
- 如果有截图/上下文：直接定位
- 如果没有：列出可能的候选，让用户选择

**示例**：
```
用户：这个按钮不好看

agent：请问是指哪个按钮？
- A. 配置页的"激活路由"按钮
- B. Profiles 页的"恢复备份"按钮
- C. Settings 页的"开机启动"开关
- D. 其他（请描述位置）
```

### 第 2 步：明确问题

搞清楚"不好看"具体指什么。

**做法**：给出常见的维度让用户选择，或开放式提问。

**示例**：
```
agent：请问"不好看"具体是指？
- 颜色不对（应该是什么颜色？）
- 大小不合适（太大/太小？）
- 位置不对（应该在哪里？）
- 样式风格（太素/太花哨？）
- 其他（请描述）
```

### 第 3 步：确定期望

明确用户想要什么效果。

**做法**：
- 如果用户能描述：记录下来
- 如果用户只能描述"不想要现在的"：提供 2-3 个可选方案

**示例**：
```
agent：我理解您希望"激活路由"按钮更醒目一些。提供三个方案：
- A. 改为 Naive UI 的 type="primary"（蓝色填充）
- B. 改为 type="error"（红色填充，强调危险操作）
- C. 保持当前样式但加大尺寸

您倾向哪个？或者有其他想法？
```

### 第 4 步：整理并请求确认

澄清完成后，**先整理成结构化需求，请求用户确认，确认后再归档到对应文档**。

**格式**：

```markdown
## 需求整理

**原始描述**：<用户原话>

**理解**：
- 对象：<具体组件/页面/功能>
- 问题：<现状有什么问题>
- 期望：<改成什么样>
- 验收标准：<怎么算完成>

**分类**：<M4/M5/M6/V1.1/V2/bug>

**影响范围**：<涉及哪些文件/模块>

**归档位置**：<TASKS.md 哪个区 / CONTEXT.md 待协调 / DECISIONS.md>

请确认：
- [ ] 理解正确，可以归档
- [ ] 理解有误，需要调整（请说明）
- [ ] 暂缓，先不做
```

**示例**：

```markdown
## 需求整理

**原始描述**：这个按钮不好看

**理解**：
- 对象：配置页的"激活路由"按钮
- 问题：当前是默认样式（灰色边框），不够醒目，用户容易忽略
- 期望：改为 Naive UI type="primary"（蓝色填充），更突出
- 验收标准：960×640 和 1120×760 窗口下视觉确认，按钮在页面中明显可见

**分类**：M4（Vue 桌面界面收尾）

**影响范围**：`frontend/src/pages/ConfigPage.vue`

**归档位置**：TASKS.md "待认领"区 M4 节

请确认：
- [ ] 理解正确，可以归档
- [ ] 理解有误，需要调整（请说明）
- [ ] 暂缓，先不做
```

**只有用户勾选"理解正确，可以归档"后，agent 才将需求写入对应文档。**

## 三、澄清结果记录

澄清完成后，在 `docs/TASKS.md` 或 `docs/CONTEXT.md` 记录时，**必须包含**：

```markdown
- [ ] [M4] 配置页"激活路由"按钮样式调整
  - 现状：当前是默认样式（灰色边框）
  - 问题：不够醒目，用户容易忽略
  - 期望：改为 Naive UI type="primary"（蓝色填充）
  - 验收：960×640 和 1120×760 窗口下视觉确认
```

**不要只写**：
```markdown
- [ ] 改一下按钮样式
```

## 四、需求归档策略

用户确认后，根据需求的规模和归属，采用不同的归档方式：

### 4.1 小需求（单个任务）

直接加入 `docs/TASKS.md` 对应位置：

- 属于当前活跃里程碑（M4/M5/M6）→ 加入对应节
- 是 bug → 加入"待认领"区，优先级标高
- 是持续性工作 → 加入"持续性工作"节

**示例**：
```markdown
### M4 — Vue 桌面界面收尾

- [ ] 配置页"激活路由"按钮改为 Naive UI type="primary"
```

### 4.2 中等需求（多个相关任务）

在 `docs/TASKS.md` 对应里程碑下创建子节：

```markdown
### M4 — Vue 桌面界面收尾

#### 表单体验优化

- [ ] 配置页"激活路由"按钮改为 primary
- [ ] 所有表单添加提交前校验
- [ ] 错误提示统一样式
```

### 4.3 大需求（需要独立规划）

如果需求超出当前活跃里程碑范围，或需要拆成多个阶段：

1. 在 `docs/CONTEXT.md` "待协调事项"记录，标注建议归属（V1.1 / V2 / 独立 goal）
2. 等用户裁决后，如果确定要做：
   - 小版本（V1.1）→ 在 `docs/planning/ROADMAP.md` 新增里程碑节
   - 大版本（V2）→ 创建 `docs/planning/V2_PLAN.md`，在 ROADMAP.md 中添加链接

**示例**（V1.1 新增里程碑）：
```markdown
### M7 — 自动更新

状态：`[ ]`

- [ ] 调研 Wails 3 自动更新方案
- [ ] 实现更新检查与下载
- [ ] 实现安装与回滚

出口标准：用户可以在应用内完成版本更新，失败可回滚。
```

**示例**（V2 独立规划）：
```markdown
<!-- docs/planning/V2_PLAN.md -->
# V2 规划：多平台支持

## 目标
支持 Claude Code、Gemini CLI、OpenCode 三个新平台。

## 里程碑
...
```

### 4.4 涉及技术选型的需求

如果需求需要引入新技术、改变架构：

1. 先整理需求，请求用户确认
2. 确认后在 `docs/DECISIONS.md` 新增 ADR
3. 再在 `docs/TASKS.md` 添加任务

**示例**：
```markdown
## ADR-0008：引入 Playwright 做 E2E 测试

- 日期：2026-10-02
- 决策人：用户 + zcode
- 状态：accepted
- 背景：M4 验收需要桌面端真实环境测试，手工验收成本高
- 决策：引入 Playwright，覆盖 Wails 桌面窗口的核心流程
- 理由：Playwright 支持 WebView2，社区成熟
- 后果：增加 dev 依赖，CI 需要额外配置
```

## 五、何时可以跳过澄清

以下情况可以直接整理归档，不用澄清：

- 用户提供了截图/录屏，且问题明显
- 用户引用了具体文件/组件名
- 用户给出了明确的验收标准（"改成和 XX 一样"）
- 是明确的 bug（功能报错、崩溃）

## 六、澄清次数限制

- 同一需求最多澄清 **2 轮**
- 2 轮后仍不明确：在 `docs/CONTEXT.md` "待协调事项"记录，标注"需求模糊，需用户进一步说明"，**暂停整理**

不要为了赶进度而猜测用户意图。猜错的代价比多问一下大得多。
